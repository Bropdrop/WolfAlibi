# Why Sovereign refuses a cold start

At 5c163f1621a687a9830632bb0e40581d2420c4a0, research/sovereign/target.py constructs an Ed25519 boot key in memory on every Stationary startup. The constructor demands the original native schema wolfalibi.shirudo.action-state.v1 and an empty operations table. First commissioning creates the authority tables and changes state.json to wolfalibi.sovereign.stationary.v1. A subsequent startup on that intact directory therefore raises TARGET_RESTART_UNRESOLVED at the schema predicate. Native Gate initialization and receipt signature validation have not yet run at the point of refusal.

TargetConnection.commit computes a seal over the authority and effect tables and the native clock. It commits the SQLite writer and assigns the seal to self.target.floor in process memory. A fresh process lacks that independently retained last value. Commands, owner permits, executor proofs and reader bindings also identify the original boot. The directory orders authority commands; it contains no complete per-write floor for the protected journal. A signed historical receipt authenticates that particular committed request. It cannot show that a candidate database contains the latest complete history. Looking at a restored file cannot distinguish it from an older valid version of the same file.

The native signing key and native gate identity persist on disk. Restoring those values or reproducing a valid SQLite integrity check cannot establish a unique current writer. A cold start needs a surviving freshness witness, an exclusive claim to the canonical protected target, a verified historical prefix and a fresh owner-authorized incarnation. The original clone refusal remains appropriate for an uncommissioned 005 volume after its live trust anchor has already disappeared.
