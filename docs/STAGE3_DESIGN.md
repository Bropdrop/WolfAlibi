# Stage 3 proposal for broker-mediated Linux execution

**Decision requested for future implementation.** Use one inherited Unix socket for access to a private synthetic resource root. Measure the worker's effective Linux isolation from a trusted supervisor. Have a verifier with independently retained state check the witness history offline. The starting revision is Stage 2 commit `37b277521041d68fa81748d41824e4c8bb66a592`, tree `fe8634e5892ffc00e3acfc5b0153ac55ba2506d2`.

The first experiment asks whether a named worker, between release of its start gate and termination of its last process, received any bytes through the broker from a specified range of path keys. Count every request for a key, including denials, conservatively against an absence claim. Exclude the worker's immutable runtime and private scratch from the protected scope. Require fresh synthetic data with no preexisting copies accessible to the worker. The scope is filesystem reads of these fixtures. Writes, directory listings, host services, preloaded data, and semantic equivalents of named files need separate coverage.

Stage 2 already verifies sealed broker epochs and can link signed witness state to a verifier's retained digest. Its launcher can demonstrate two marker exclusions. Process-wide mediation, measured code identity and independently operated witness custody are open requirements. Preserve `BROKER_ONLY` on existing receipts and `BLOCKED` for requests for stronger assurance throughout this experiment.

## Process boundary and protocol

1. The verifier issues a fresh 256-bit challenge, a unique run ID, the allowed policy digest, resource manifest digest, expected program digest, pinned signing keys and its last accepted history head. Record challenge issuance and expiry transactionally at the verifier. A failed or interrupted run retires its challenge.
2. The supervisor creates a private read-only synthetic corpus, a separate broker state directory and fresh worker scratch. Pin a single supported static worker binary in a read-only runtime. Bind its measured executable identity to the supervised process and run ID. Use separate namespaces for mounts, PID, IPC and network, a private mount propagation policy, an unprivileged identity, dropped capabilities and a restrictive syscall policy. Require kernel support for all controls selected by the profile. The worker and its descendants must lack a route to the protected root, journal, signing keys or witness service except for allowed broker operations.
3. Create a connected `AF_UNIX/SOCK_SEQPACKET` socket pair per run before launching. Pass exactly one endpoint across exec. The broker owns the other endpoint. Keep stdin on a null device and send stdout/stderr to bounded supervisor-owned sinks. Prohibit opening new communication endpoints and transferring descriptors. Treat possession of the private endpoint as authorization only for this run's allowed requests. Put keys and witness control traffic in separate processes outside the sandbox.
4. Use a versioned, bounded packet with run ID, strictly increasing request number, operation and canonical root-relative key. Define exact byte encoding, packet and response size limits, one request in flight, and allowed operation `READ`. Validate truncation flags, lengths, opcodes and ancillary data before dispatch. A key outside the policy yields a durable denial. An unclassifiable packet, duplicate number, gap, timeout, unexpected control message or ambiguous disconnect invalidates the run. Avoid retries that could duplicate a release.
5. Dispatch through the existing rooted broker and WAL. Bind request number, run ID and key to a write-ahead record durable before release. Record response length and completion separately. An interrupted delivery still counts against absence. A durable authorization record and a completed socket send have different meanings. Never infer that the worker consumed the bytes from either record.

## Run boundaries and measurable evidence

Stage 3 should initially support one run and one worker process per broker. Start it at a trusted gate with only a measured bootstrap executing. Hold the worker until the supervisor observes the controls below and the witness acknowledges the signed start record. Bind the identity of the executed image to a stable process handle, and enforce or measure the transition to that image. If the host cannot supply that binding, record the declared digest separately and block the execution-boundary claim.

| Required observation | Record for independent checking | Acceptance condition |
| --- | --- | --- |
| Worker's filesystem and network views | Effective mount table and mount flags, namespace identities relative to supervisor, runtime identity and local interface/route inventory | Exact approved runtime and scratch mounts. Private protected root and host sockets excluded. Network policy enforceable locally. |
| Effective authority | UID/GID, capability sets, no-new-privileges status, loaded syscall policy digest with trusted installation result, and pre-release descriptor inventory | Exact expected credentials, policy and descriptor types including the run endpoint. A reported seccomp mode alone cannot identify the filter. |
| Protected corpus | Supervisor-owned private mount and synthetic fixture manifest, frozen for the run, canonical path-key policy, alias and mount checks | Single approved source with immutable names and content for the interval. Refuse ambiguous aliases or uncontrolled mutation. |
| Interval and completion | Signed start, gate release, monotonic event counters, broker request range, stable process identity, exit status, process-group containment and final seal | Start acknowledged before work. All workers and descendants accounted for, admission closed, broker drained, terminal seal durably witnessed. |

Use a dedicated, supervisor-owned process scope (for example a delegated cgroup v2 subtree) with child migration prohibited. A parent exit or socket EOF alone cannot close the evidence interval. For the initial single-process profile, forbid process creation and still require an observed empty scope before issuing the terminal record. On timeout, clean up the scope, drain or close the endpoint and mark the run incomplete. After a restart, preserve records for inspection. An interrupted run can finish with a failure record, never with a synthesized successful boundary.

The supervisor signs its measurements separately from the broker and witness. Bind their digests, policy, corpus, challenge, run ID and checkpoint interval into one versioned evidence envelope. Include kernel and launcher versions for reproduction. A reader should be able to identify which observations depend on trust in the supervisor and Linux kernel. The witness can check the event sequence but cannot observe host accesses omitted by both supervisor and broker.

## Independently verifiable history

Use a distinct witness process with its own key and storage inaccessible to the worker and broker. Give the verifier a separate persisted, authenticated history head. For the first local experiment, use a linear signed history so a verifier can check each transition without a new proof system.

- Define canonical, length-delimited records with version and signature domain, witness and broker identities, history index, previous record digest, event type, run ID, challenge digest and event payload digest. Sign start, checkpoint, finish or abort, and receipt-retention records. Bind each checkpoint to its predecessor and epoch/sequence bounds. Each record describes its transition so the verifier can check which run and broker it advances.
- Before acknowledging a transition, validate it against durable state and append and sync its record. Recover the head and receipt index from the committed log. For idempotent recovery, an exact repeated request returns the original acknowledgement. A conflicting request at an occupied index fails closed. A post-crash record with ambiguous durability blocks any dependent claim.
- Before signing each checkpoint, reuse the existing witness checks for sorted leaves, Merkle root, event counts, predecessor and contiguous sequences. Reconcile those counts with the supervisor's run-bound admission and drain records. Document which inputs were supplied by the broker and which were observed at the supervisor.
- Export the chain suffix from the verifier's prior head to the terminal signed head, plus the signed lifecycle records and Merkle proof. Hash the receipt payload before appending its retention event, and carry that acknowledgement outside the hashed payload. This avoids a circular hash dependency. Set a maximum suffix size and fail explicitly when a usable history segment is unavailable.
- The offline verifier checks pinned keys, freshness and scope, prior head, record ordering and linkage, lifecycle transitions, sequence coverage, measurement bindings and Merkle proof. Advance its stored head and consume the challenge together using compare-and-swap. A competing update requires revalidation. An identical receipt may be inspected again as historical evidence, but cannot complete a second fresh challenge.
- A fresh verifier needs an independently delivered trusted starting head. Two isolated clients can otherwise receive conflicting signed histories. Cross-verifier head comparison or a separately administered checkpoint archive is a later milestone. Separate local processes model custody and restart behavior under one trusted host. Independent administration remains unqualified.

## Local qualification plan

Use temporary synthetic fixtures throughout. Record exact Git tree, kernel, launcher, profile digest, fixture digest, commands, observations and outcomes in a JSON transcript. Keep controls with unavailable prerequisites visible in the results.

| Local case | Required observation |
| --- | --- |
| Allowed broker read, disjoint protected range | Known synthetic bytes arrive over the run endpoint, the request is durable, and the broker proof verifies for the disjoint range. |
| Request inside protected range, including a denial | The recorded key prevents an absence proof. Missing or truncated completion data yields an incomplete run. |
| Effective isolation and prerequisites | A visible scratch marker provides a positive control. The external marker and an intentionally inheritable synthetic canary FD are absent. Independently compare effective mounts, namespaces, capabilities and descriptors. Missing kernel facilities yield `UNSUPPORTED`. |
| Boundary timing and supervisor restart | An in-flight broker request delays sealing. An unresolved worker, pending operation or supervisor restart prevents a successful terminal envelope. |
| Witness crash, rollback and concurrent verification | Restart from durable history and reconcile an exact retry. A stale head, gap, fork, stale challenge or failed verifier head update prevents acceptance as fresh evidence. |
| Evidence substitutions | Changing the run, program, policy, range, measured controls, checkpoint or witness key invalidates the envelope against independently supplied references. |

Implement in three reviewable increments. First demonstrate the supervised socket route and pre-release logging with known fixture bytes. Next capture effective controls and enforce the end-of-run barrier. Finally add history export, a separate verifier store and offline replay of the transcript. Keep protocol and history checks runnable locally even on a host that lacks the Linux profile. The exit criterion is a reviewer reproducing each observation and its failure condition. Changing the production assurance level requires a separate security review.

Implement the supervisor alongside [the Stage 2 launcher](../wolfalibi/isolation.py), dispatch resource reads through [the existing broker](../alibi.py), and add the experimental envelope as a separate version alongside [the v1/v2 verifier](../wolfalibi/receipts.py). Report broker verification, confinement observations and witness continuity in separate machine-readable fields. For each required control, retain its expected value, observed value, evidence source and outcome. Use `UNSUPPORTED` for an unavailable mechanism, `BLOCKED` for missing or incomplete required evidence and `REJECTED` for contradictory or invalid evidence.
