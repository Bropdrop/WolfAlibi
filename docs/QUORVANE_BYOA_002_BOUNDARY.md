# BYOA 002 · who controls the evidence?

An authorized operator runs a reviewed decision function in the measured BYOA 001 cell. A separate experiment asks whether a live gateway carrying evidence from that run may obtain one additional fictional release from a resource owner. These are operations at different times. The gateway makes the second request. The selected Python entrypoint consumes its staged response inside the earlier cell. The historical trial, verifier challenge, owner grant, target response and signed receipt each answer different questions.

## Actors and assumptions

| Principal | Asset or decision under its control | Independent input that another principal needs |
| --- | --- | --- |
| Operator and gateway | Selects and consents to the reviewed source, runs the supervisor and broker, and requests the exact operation. The operator protects its request-signing key. | The owner and verifier need an authenticated operator key, approved program and policy. The owner also needs the measured identity of the live gateway. An approval copied from a previous process cannot establish current authority. |
| Verifier | Chooses the fresh challenge, retains the pre-run expectations and witness reference, and checks the later evidence against its retained state. | The owner and operator need the verifier's authentic public key and the exact approved scope. The verifier needs the owner's authentic public key to check the resulting decision and a retained reference to check history. |
| Resource owner and target | Holds its own signing material, revocation state and authoritative ledger. Checks each proposed operation. Owns the protected synthetic value and signs the disposition. | The gateway and verifier need an independently obtained owner pin. The gateway additionally checks the target endpoint and process identity. A signing key supplied inside an otherwise self-consistent packet cannot authenticate the owner. |
| Host administrator and kernel | Control accounts, boot, storage, process visibility, time, namespaces, socket credentials and permissions. | Ordinary signed JSON cannot establish the integrity of this platform or the independence of its administrators. Use the assigned, pre-provisioned accounts and compare their evidence separately. |

The three parties exchange public keys and expected file digests over a channel whose authenticity they establish outside the experiment. Public enrollment records, grants, evidence and signed replies may travel over a different local handoff. Each recipient checks the packet against the previously held input. A packet containing a new key and a signature verifiable with that key only shows internal consistency. Each party keeps its private directory and retained state. Combining all roles under one UID demonstrates protocol behavior conditional on an honest local operator.

## What is measured

The 001 supervisor samples its waiting worker using pidfd and procfs. The signed record covers the executable, launched program, namespaces, mount table and bind identities, capabilities, descriptors, limits, seccomp mode and filter count, and observed lifecycle. The fixed direct-file, socket, fork and exec probes report from inside the bootstrap. Its broker journals a read before sending bytes. The selected function starts later and receives those staged bytes through one observed callback. The trusted runtime, kernel and bootstrap implement these controls. The optional LangChain driver runs outside that cell.

The 002 owner examines the live gateway over a local Unix endpoint. The gateway is the peer the target observes. The signed 001 supervisor snapshot describes a different process. Fresh supervisor evidence can satisfy a qualification condition at the target. It cannot identify the earlier selected entrypoint as the process that requested the additional release. The second response is a fixed fictional value visible in the source. The protected effect in this experiment is the service committing the operation, authorizing and attempting handoff. This profile cannot establish secrecy of the fixture bytes. Neither operation establishes settlement.

A sampled interpreter, command line and trusted script path identify the agreed gateway launch profile under the host assumptions. A file hash collected from a pathname cannot authenticate all historical Python bytecode, native libraries or process memory. The host must protect the trusted checkout and interpreter from unauthorized changes throughout execution. Required procfs access depends on local policy. An unavailable mandatory observation must stop that path.

The two demo ceremonies each enroll a fresh set of 001 role keys and the exact witness genesis. Consecutive real 001 workers on one advancing, independently retained witness lineage were not demonstrated.

The verifier reserves an unpredictable nonce and run ID before approving the complete expected contract. The 001 report binds that nonce. It does not contain the bytes of the later 002 approval signature. The demo starts the worker after approval. An independent reader cannot cryptographically order a worker started after nonce disclosure and the later approval within the same integer-clock second. The target still requires the verifier's signed approval and current state for the second release.

The owner checks the exact signed inputs, measured peer and live verifier before committing its receipt. Verifier retention then advances the witness head. The target rechecks current authority and peer before giving a response body to the socket handler. A committed receipt can survive a later revocation or retention failure without data handoff. The transport sends bytes after the final target check. Historical verification can establish a retained commitment; actual recipient delivery remains `NOT_ESTABLISHED`.

## Failure interpretation

| Scenario | Evidence and residual risk |
| --- | --- |
| Malicious gateway or altered public packet | Compare the owner decision, authoritative effect count, original receipt and independently retained references. A client exception or timeout alone cannot demonstrate a target denial. |
| Compromised supervisor, witness or signer | A signature authenticates what that signer endorsed. It cannot establish the truth of a compromised supervisor's observation or the completeness of records omitted by the broker. Affected keys and evidence require separate revocation and review. |
| Loss after commit, before acknowledgement or publication | Reconcile the exact operation under the signed historical request. Compare the recovered receipt bytes or canonical digest with the owner's original. A committed effect can survive an absent public report. A lost reply leaves delivery ambiguous and does not authorize redispatch. |
| Old database or competing heads | Retain a reference under a separate principal and compare it when reopening. Conflicting histories or missing required records must withhold positive claims. A reference file beside the database shares its rollback exposure. If owner revocation state and the checkpoint both roll back before the verifier sees any commitment, protection against the lost revocation is unassessed. |
| Coordinated rollback or malicious administrator | A party able to revert every trusted store, external reference and clock can present a self-consistent old view. In the direct joint-restore control, restoring target and verifier databases plus checkpoints to their pre-dispatch state produced a second release on the unpinned cold-restart path. The restored ledger contained only one commitment. A verifier supplied with the separately retained newest head refused the same restored state before release. Ordinary file permissions cannot constrain the host administrator. Detecting coordinated restoration requires authenticated records under genuinely separate control. |
| Application counters or callback reports | Identify the source of each observation. SDK counters, worker probes, supervisor samples, owner ledger entries, target receipts and the verifier's disposition have distinct provenance. |

## Evidence required for stronger claims

On the available Linux account, the test operator has UID/GID 1000 and zero effective, permitted and ambient capabilities. An independently provisioned, authorized second account is unavailable. Visible service accounts, namespace UID mappings and subprocesses started by this user cannot stand in for another custodian. Independent resource custody remains `UNSUPPORTED`.

A genuine two-account test requires the enrolled gateway and resource-owner identities, a successful operation through the pinned live endpoint, a wrong-principal refusal with an unchanged owner ledger, four actual kernel-denied gateway opens of the target signing key and ledger, and the original signed disposition after target restart and response loss. The owner independently checks object identities and ledger history. If the kernel withholds a mandatory cross-user process observation, record `UNSUPPORTED` and the failed prerequisite. The verifier has a separate custody requirement for its challenge, signing material and retained history. Two different UIDs alone cannot establish three independently administered principals.

Untrusted third-party execution needs a separately approved disposable environment, a pinned runtime and dependency closure, independently measured boot or another external trust anchor, policy-bound communications, full-lifecycle descendant and resource accounting, and measured teardown. This experiment does not qualify a microVM. Formal certification also needs public assessment criteria, an independent issuer and procedures for reassessment and withdrawal. Operational confinement and production are `BLOCKED`. Certification is `NOT_ISSUED`.
