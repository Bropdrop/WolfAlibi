# BYOA qualification 001 · trust boundary

This trial concerns a consenting operator's reviewed local Python entrypoint, a single synthetic fixture and a particular measured Linux process. A callback can report an invocation. A broker can attest to its own durable record. The protected resource owner decides which effects are permissible. These are different claims with different evidence.

## Where code and authority live

| Component and actor | Execution location and authority |
| --- | --- |
| Operator and provider of the submitted bytes | Outside the cell. Selects the local package, approves the exact identity, consents and controls the source checkout. Review the source before running it. The profile accepts a restricted Python entrypoint with a declared tool and a closed dependency inventory. It supplies no general Python import, plugin discovery or package installation feature. |
| Supervisor and trusted bootstrap | The supervisor and Bubblewrap launcher run on the host. Trusted CPython and bootstrap code start in the new namespaces. The supervisor compares the child and its launched program to the enrolled profile before the protected release. The entrypoint's authority is bounded by the admitted language and declared tools, the reviewed bootstrap, and the kernel controls. Trusting the bootstrap is necessary even when its bytes match the expected hash. |
| Agent callback and wrapper | Run inside the measured worker for the supported entrypoint. The wrapper observes calls through its own interface. Its aggregate and denial probes originate within the process. They cannot account independently for every instruction, access, error or child. |
| Broker, supervisor signer, witness | Host-side. The broker owns the declared read, appends to its WAL and returns fixture bytes over the per-run Unix endpoint. The supervisor samples the live process and signs its observation. The witness checks broker commitments and advances a retained head. Its view is limited to the records submitted by the broker. The host fixture setup, layout read and canary open are also outside the cell. |
| Owner and protected service | Owner approvals, credentials, protected data and target decisions belong outside the worker. A grant must specify the exact operation and identity and must be current at the decision. A completed worker's signed history cannot substitute for a live caller or an owner grant. |
| Reviewer | Outside the cell. Rechecks the signed historical report against separately retained expectations and role keys. An expectation file delivered by the report producer can demonstrate local consistency. The reviewer must establish its provenance before making an independent claim. Local timestamps, measurements and terminal events remain statements by their respective signers. |

### A protected read in this profile

1. A trusted loader opens the manifest and the exact two-file package using directory-relative file descriptors. It retains the validated bytes and checks the sole allowed callback dependency. The entrypoint is `<package>.agent:run`. The selected file contains a bounded, loop-free Python decision function. The declaration and approved source become part of the externally expected launch contract. [Bundle validator](../wolfalibi/byoa_bundle.py)
2. The host launches the trusted Solitary worker. Its measured command-line program includes the captured source bytes, bootstrap and adapter. After loading its filter, the bootstrap makes the initial broker request. The supervisor locates the waiting live process and measures it. **The bootstrap initiates this request.** The submitted entrypoint has not started. [Cell](../wolfalibi/byoa_cell.py)
3. At provisioning, the target administrator enrolls the five distinct public role keys once in the target's checkpointed SQLite ledger. The target compares the submitted expectations to that enrollment. Its admission code authenticates the owner grant, current run/challenge, policy, signed successor of the retained witness genesis for this run marker, and measured live caller. It commits its decision in the synthetic target ledger and anchors the decision before control returns to the broker. The broker appends its own WAL record before sending the synthetic data. Target admission time and the last pre-handoff clock sample precede WAL recording and transport. The target lease serializes revocation and admission. No continuous clock observation spans the final byte delivery. The target gate and the supervisor share a host process and OS identity in this experiment. [Read gate](../wolfalibi/byoa_effect_gate.py)
4. The trusted adapter checks the received fixture digest, then compiles and calls the approved decision function inside the worker. Its single `read_fixture` tool returns the already staged bytes. The bootstrap retains the socket and the host retains the credentials and signing keys. Exactly one completed wrapped call and an acceptable decision are required for the successful profile. The callback count and the target's earlier admission have separate provenance. [Bootstrap](../wolfalibi/byoa_cell_bootstrap.py)
5. Terminal evidence covers the submitted program's acknowledgement and closed lifecycle. A target admission by itself proves neither release nor callback completion. The final verifier binds the signed historical report to externally supplied expectations, checks the separate target admission and the broker/witness/supervisor evidence, and labels the aggregate as observational. Historical rechecking confers no current authority. [Attestation](../wolfalibi/byoa_attestation.py)

### How LangChain drives the same trial

With `--framework langchain`, a trusted local SDK process runs LangChain 1.5.2 and langchain-core 1.8.4 outside Solitary. Its scripted in-memory model invokes one registered tool, `request_trial`, with no arguments. The host supervisor receives that request on a private Unix socket and invokes the ordinary BYOA admission and execution path above. Only the supervisor receives the operator's CLI arguments and role references. The SDK receives the resulting completion or refusal status. The SDK's temporary working directory, restricted environment and disabled tracing limit incidental exposure. The SDK still executes under the host user's filesystem permissions. [Linked framework driver](../wolfalibi/byoa_langchain.py)

The two counters refer to different calls. The SDK observes one host-side `request_trial`. The measured Python worker observes its own `read_fixture`. An ordinary LangChain tool return can carry a refusal from the protected trial. Publication of the separate `framework-observation.json` requires a completed inner report that verifies against the pre-run expectations. This unsigned observational sidecar identifies the inner report by SHA-256, run ID and challenge. The signed historical report stands on its own with the external expectations. Other Stage 4 SDK integrations retain their original host-side coverage.

## What a measurement means

The inherited Solitary supervisor samples a specific direct child using procfs and pidfds. The record includes launch arguments, the digest of the launched CPython executable and program, UID/GID maps, five capability sets, supplementary groups, threads, tracer and `NoNewPrivs`. It checks the six user, mount, PID, network, IPC and UTS namespace links. Mount checks include the full observed mount list, root type, flags and the expected bind-source device/inode identities. The read-only bind mounts include the interpreter, standard library directory, native library directory and dynamic loader. The runtime binds are read-only and the worker has a private writable tmpfs root for its scratch probes. Authenticating the complete contents of either library directory would require an additional image or per-file inventory. [Process measurements](../wolfalibi/stage35_measure.py) · [Launch profile](../wolfalibi/stage3_worker.py)

The supervisor also checks that FD 0 names the expected socket inode and that FDs 1 and 2 refer to the null device, samples soft/hard resource limits and compares the exec environment with the sole permitted `PWD` entry. It observes seccomp mode 2 and a filter count greater than the launcher's. Filter identity and installation order depend on the trusted bootstrap. The worker performs the fixed direct-file, socket, fork, exec, scratch and resource-limit checks. Those individual syscall results are **worker reports**. They are compared with the expected controls, then signed alongside the separately collected kernel snapshot. A trapped process or an unavailable measurement contributes no positive denial. [Worker and filter](../wolfalibi/solitary_worker.py) · [Envelope verification](../wolfalibi/solitary_evidence.py)

The launcher exit, worker pidfd exit, endpoint hangup and drained packet queue are the observed terminal boundary for this process. A missing terminal record can coexist with a durable read in the WAL. Check the journal and an independently retained head when reconciling an interruption. There is no continuously observed process tree, hardware attestation, or cgroup-wide termination proof. Code and fixture metadata in the worker launch arguments may be visible through procfs to an authorized host principal. Supply no confidential source, credentials, real financial information or personal data.

Independent custody, untrusted submissions and certification require further evidence. [Qualification gap analysis](QUORVANE_BYOA_GAPS.md)
